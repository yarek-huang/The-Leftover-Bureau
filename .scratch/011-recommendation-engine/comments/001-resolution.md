# Resolution

## 推荐引擎设计（Yk 定案，2026-08）

### 匹配算法骨架：规则打分器 + LLM 判断组合

1. **规则打分器**（不依赖 LLM）：对食谱库做主料覆盖率 + 临期加权 + 口味信号打分，产出候选集。
2. **LLM 判断**：对候选集做语义匹配（容忍自由文本名差异）+ 组 2-4 菜套餐 + 剩菜改造分支。
3. 库空/无匹配时，极速清场降级为 LLM 现场生成"出清方案"（与饕餮盛宴共用生成路径，prompt 目标不同）——013 已定。

### LLM 调用

- **结构化 JSON 输出**（007 已核实 GLM json_object 模式 + Pydantic 校验 + 带错误反馈的重试 + 失败降级，但见 Q4）：
  `[{recipe, reason, match_score, missing_main?}]`。
- 走 provider 抽象层（007 建议的 LiteLLM 库形态，`recipe_generation` 槽位）。

### 同步/异步

- 极速清场**同步**，饕餮盛宴**异步**（可能几十秒，任务 + 前端轮询）。

### LLM 不可用：不降级，直接报错（Yk 明知取舍）

- **后果已确认**：自由文本食材名要靠 LLM 做语义匹配，纯规则无 LLM 时退化为精确字面匹配（番茄/西红柿/小番茄对不上），基本不可用——故 V1 推荐是 **LLM 硬依赖**，两模式皆然。内网有 GLM/DeepSeek 可用，接受此依赖。

### 权重：可调

- 临期加权与口味信号权重**可调，用户自己配**。默认：临期命中必进候选，口味信号作同分决胜；用户可在设置里改。

### 缓存（Redis）

- 按**冰箱食材签名**缓存 LLM 响应：同组合重复推荐命中缓存，食材变动（增删改/到期日变）时失效。
