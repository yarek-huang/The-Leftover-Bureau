# Resolution

## 食谱与推荐的领域模型（Yk 定案，2026-08）

### Recipe 实体（精简字段）

- **字段**：名称 / 食材清单 / 步骤 / 总耗时 / 人数份量 / 难度（易/中/难）。
- **不建标签体系**：菜系/口味等不设用户维护的标签维度。
- **食材清单行**：自由文本名 + 自由文本用量 + **主料/调料标记**（自建用户标、AI 生成时模型标、可改）。
- **难度/耗时**：自建由用户填；AI 生成/种子由模型填；均可后补。
- **派生字段 荤/素**：入库时 AI 顺手标注（派生、可改），仅供套餐荤素搭配用，不算用户标签体系。

### 极速清场匹配规则

- **调料/基础料（油盐酱醋等）默认家家都有，不阻碍匹配**；只对主料要求"在库"。
- 主料必须全在或差一样：全在即匹配；差一样时**仍推但附补购单件数**；差两样以上不推。
- 匹配对象是 004 决定的自由文本食材名——匹配必须容忍字面差异（**LLM 语义匹配**，不靠精确 ID/字典）。

### 饕餮盛宴生成边界

- **库内检索优先**：先从平台库 + 用户私有库匹配高配菜；不够用时 LLM 现场生成，并**自动存入私有**（与 002 Q10 一致）。

### 推荐结果形态：套餐制

- 一次给 **2–4 菜搭配方案**（荤素搭配），非单菜。组套逻辑（荤素搭配约束 + 临期加权）属推荐引擎工程细节，留给 011。

### 口味学习信号（进 V1）

- 卷宗历史（做过什么 + 评价）作为推荐偏好信号：常做的菜加权、被差评的菜降权。简单规则起步。

### 剩菜/熟食特殊逻辑（题眼）

- 剩菜条目优先**"翻热即可"或"改造重做"建议**（如剩红烧肉→烩面），不硬套生鲜食谱。改造建议走 LLM 现场生成，存私有。

## 域词汇（已同步 CONTEXT.md）

Recipe（含主料/调料行、荤素派生字段）、MealSet（套餐推荐：2-4 菜搭配）、Taste Signal（卷宗偏好信号）、Leftover Rework（剩菜改造/翻热）。
